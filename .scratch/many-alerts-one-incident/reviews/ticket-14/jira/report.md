## 2. There is no way to write to an existing Incident

**Partly holds as a Skill gap; fails as a CLI or permission-boundary impossibility.** The Skill already writes comments and transitions existing issues ([SKILL.md:119–120](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:119), [151–169](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:151)). Inline fields require no file-writing tool.

**The objection's proposed command is wrong on this installed v2 build.** A full CLI invocation intercepted before transport constructs:

- `--field 'update.labels[0].add=fp-example'` → `{"update":{"labels[0]":{"add":"fp-example"}}}` — a literal `labels[0]` field, not the labels array.
- `--field 'update.labels=[{"add":"fp-example"}]'` → `{"update":{"labels":[{"add":"fp-example"}]}}`.

See [cli-request-construction.txt:1–7](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/cli-request-construction.txt:1). `issue update --labels` really replaces the whole label set ([cli.txt:199](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/cli.txt:199)). This can lose earlier Fingerprints, but replacing one fp label with another does **not** make reset lose ownership: reset accepts *any* `fp-` label ([reset.py:92–95](/Users/jasonkrueger/projects/many-alerts-one-incident/grafana_jsm_sandbox/reset.py:92)).

**Smallest D4/D5/D6 correction:** explicitly require additive membership edits and field updates, with read-back before relying on them. A command whose request construction was verified offline is:

```bash
jira-as api call editIssue --issue-id-or-key '<key>' --field 'update.labels=[{"add":"fp-<fingerprint>"}]' --field 'fields.customfield_10085.value=Sev-1' --field 'fields.customfield_10079.value=Critical'
```

The Severity/Urgency fields are included only when the comparison requires that promotion. Read current fields first; do not replace labels with only the new member. A failed update must not be treated as a successfully registered member or applied ratchet.

**OPS editability remains unverified, not refuted.** The local self-documentation itself conflicts: the imported endpoint description says screens are not checked ([cli.txt:60](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/cli.txt:60)); the behavior note still says fields must be editable on the issue screen ([cli.txt:115](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/cli.txt:115)). ## 4. Per-Fingerprint resolved state has no defined durable home

**Holds as a missing decision detail; fails as a claim of inherent inability.** ADR 0006 requires persistent membership labels and Reports growing across Runs ([ADR 0006:9–11](/Users/jasonkrueger/projects/many-alerts-one-incident/docs/adr/0006-one-incident-per-fault-and-match-is-a-judgment.md:9)); the existing Skill processes each Alert independently and closes on a matched resolution ([SKILL.md:8–10](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:8), [50–56](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:50)). Its comments store a scalar trend and an aggregate firing count, not a per-member state schema ([SKILL.md:114–120](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:114), [142–148](/Users/jasonkrueger/projects/many-alerts-one-incident/skill/incident-sync/SKILL.md:142)). Membership alone therefore cannot evaluate D6 across Notifications.

**Smallest D6 correction:** specify durable state separately from membership. A small label-based option is immutable `fp-<f>` membership plus `done-<f>` for the latest processed resolved state. Add done on Resolved; remove it on a later Firing; never remove membership on resolution. Read the label set and complete normally only when every fp member has its matching done marker. Both add and remove JSON-array payloads construct correctly ([body-parser.txt:6–9](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/body-parser.txt:6)).

The objection's add-only done proposal is insufficient: current captures contain resolved→firing transitions, and a permanent “ever resolved” bit would falsely clear a re-fired member. Examples are [payment:16](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/notifications-paymentUnreachable.jsonl:16) and [payment:20](/Users/jasonkrueger/projects/many-alerts-one-incident/.scratch/many-alerts-one-incident/reviews/ticket-14/jira/notifications-paymentUnreachable.jsonl:20). D3's coalesced input needs an ordering/latest-state contract for repeated occurrences of the same Fingerprint; “Firing first” alone is not an event-order definition. Missing/failed state updates cannot count as resolution. This is a proposed representation, not a claim that Jira lacks other stores or that structured comments are impossible.
