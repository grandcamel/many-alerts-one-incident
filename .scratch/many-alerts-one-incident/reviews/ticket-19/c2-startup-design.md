## Packaging decision

Use the existing pinned LGTM amd64 image as the candidate source of binaries, but propose **four separately managed containers**, each invoking its required binary directly: Grafana, Loki, Prometheus and Tempo. Each receives an explicit read-only config. Do not invoke the bundled `run-all.sh` or component wrappers. Reusing one pinned image avoids introducing four unverified registry inputs; it does not prove the image works with the proposed UID, mounts or configs. No derivative image is required by this design yet, and no digest or readiness result is invented.

The [tagged launcher](https://github.com/grafana/docker-otel-lgtm/blob/v0.33.1/docker/run-all.sh) starts Pyroscope and the collector in addition to the four required services. It also bootstraps a Viewer account/token and writes MCP integration files. That conflicts with the experiment's exact operator-owned credential inventory. Its readiness loop has no overall deadline. A custom operator will own bounded readiness and credential creation instead.

The Grafana wrapper defaults anonymous access to Admin, writes a plugin-version marker under `/data/grafana`, and unconditionally adds a plugin preinstall request. The collector wrapper can generate a config overlay in the image working directory and enable external exporters from environment. Direct binary invocation avoids those wrapper side effects; the actual application defaults still need explicit configuration and runtime inspection. Omit Pyroscope, the collector and OBI from this experiment's process inventory.

## Proposed executable, storage and network contract

All four backend containers use UID/GID 2000, read-only root, no capabilities, no-new-privileges and no published ports. UID 2000 executable/config readability must be measured after a separately authorized image pull. Use explicit Docker tmpfs ownership for writable data and temporary directories; never make the image root writable to accommodate a startup failure. Proposed per-container ceilings are one CPU, 128 PIDs, 1 GiB memory with MemorySwap also 1 GiB (no additional swap allowance), a 256 MiB data tmpfs and a 32 MiB `/tmp` tmpfs. Set Docker logging to `json-file` with `max-size: "2m"` and `max-file: "2"` for each of the four backends, with no inherited daemon defaults. Inspect the actual `HostConfig.LogConfig`, account for up to 16 MiB aggregate rotation targets plus overhead outside container memory/tmpfs, and export at most 4 MiB per backend inside the supporting evidence budget. A log file can exceed its rotation target by a single record, so this is not a hard aggregate host-disk bound; reject unexpectedly large records/exports and record truncation or incomplete evidence explicitly. These are candidate limits requiring host-capacity and startup verification before a final card; exceeding them stops readiness rather than increasing them automatically.

| Service | Direct executable in pinned image | Required writable state | Proposed listeners / routing |
| --- | --- | --- | --- |
| Grafana | `/otel-lgtm/grafana/bin/grafana server` | `/data/grafana` for SQLite, plugins/cache; console logs | Port 3000 on experiment internal network; gateway's fixed numeric target is this instance only |
| Loki | `/otel-lgtm/loki/loki` | `/data/loki` for chunks, rules, TSDB/WAL after explicit config audit | HTTP 3100 on internal network; ring/memberlist/gRPC need single-instance config validation |
| Prometheus | `/otel-lgtm/prometheus/prometheus` | `/data/prometheus` TSDB | HTTP 9090 on internal network; enable only required OTLP receiver; no scrape jobs or remote-write targets |
| Tempo | `/otel-lgtm/tempo/tempo` | `/data/tempo/wal` and `/data/tempo/blocks` | HTTP 3200 and OTLP/HTTP receiver on internal network; single-instance internal gRPC/ring endpoints need explicit config |

Unlike the bundled shared process namespace, separate containers cannot use the tagged configs' `127.0.0.1` cross-service URLs. The operator must freeze actual container/network IDs and numeric addresses, then render Grafana data-source config for UIDs `prom`, `loki`, `tempo`. Gateway accepts only the frozen Grafana address/port; the Run retains its separate network-none namespace. All actual backend/gateway IPs and declared ports enter the Run denial probes, including the ingestion port. Compose service-name resolution alone is not the fixed-target evidence.

Grafana must use an explicit home path `/otel-lgtm/grafana`, read-only provisioning directory and writable data path. Disable anonymous access and sign-up. Keep admin bootstrap credentials in a protected operator-supplied file, never command arguments or image/environment dumps. Disable plugin preinstall/automatic updates/key fetching and analytics/update checks; the [pinned Grafana defaults](https://github.com/grafana/grafana/blob/v13.2.1/conf/defaults.ini) expose these controls. Empty plugin lists alone do not override the bundled wrapper; this is another reason to bypass it. Keep built-in data-source plugins readable, console logging bounded and the experimental network internal. These controls remain a proposed config, not an observed absence of outbound attempts.

The [tagged Tempo config](https://github.com/grafana/docker-otel-lgtm/blob/v0.33.1/docker/tempo-config.yaml) enables metrics generation and remote write. The C2 config should omit that unrelated pipeline and explicitly configure local trace storage and the required receiver. This needs version-specific config validation. Do not copy old all-in-one localhost addresses or assume all persistence defaults fall under the listed data directories.

## Seed integration and acceptance boundary

Choose and freeze a recent UTC `T0` before runtime. The offline generator accepts it explicitly and never samples a clock, sends data, creates credentials or retries ingestion. The proposed pipeline is Loki JSON push, direct Prometheus OTLP/HTTP metrics, and direct Tempo OTLP/HTTP traces. Prometheus documents the OTLP receiver endpoint in its [OpenTelemetry guide](https://prometheus.io/docs/guides/opentelemetry/); payload encoding follows the [OTLP specification](https://opentelemetry.io/docs/specs/otlp/). Exact pinned receiver acceptance remains untested.

A future operator must validate T0 freshness against the frozen backend configs, hash the generated manifest, submit each payload once within a bounded setup phase, and query the exact expected data until readiness succeeds or its deadline expires. Readiness polling is read-only: no silent re-seeding, changing windows or replacing IDs. Freeze metric translation/label behavior before matching PromQL results. Preserve multiline log suffixes, the complete trace-membership set, precise log timestamps, metric evaluation times and trace parent-child structure in operator ground truth. Never mount the expected answers into the Run.

The backend evidence design remains distinct from C1's synthetic receipt emitter. Retain ingestion request hashes and exact read-back results, available application access logs, gateway/Forwarder hashes and native MCP frames; do not call these a three-role backend receipt join. The subsequent offline oracle validates exact Loki rows/labels/multiline content and standard Tempo trace relationships and timing. Public Prometheus acceptance remains blocked pending effective label compatibility; native Tempo LLM output remains unsupported. The next source batch binds resolved configuration output to an injected transport driver. Full C2 policy and real HTTP integration, authenticated account lifecycle, pinned-image configuration read-back, durable ingestion intent, complete create/remove inventory and C1 remaining-check reconciliation are still required before an execution card.
