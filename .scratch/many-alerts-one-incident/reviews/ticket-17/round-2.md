# Ticket 17 — second decision round accepted

The human answered “agree” to all six second-round recommendations, after accepting all five first-round architecture decisions. The current implementation remains the single-site HTTP Forwarder described in facts.md. These recommendations concern the planned multi-service sidecar, not verified client behavior.

1. Endpoint addressing. Use distinct loopback HTTPS ports for the Jira, Confluence, Grafana and Kubernetes service endpoints, each bound to a fixed upstream origin. Preserve native client API paths rather than require routing prefixes; Confluence keeps its /wiki path. The listener selects the service, and the request must also carry that service's sentinel. Explicitly test wrong-port/wrong-service rejection and native base-URL/path handling. Exact port numbers are specification details.
2. Trust material. Operator-controlled deployment tooling creates the local CA and endpoint certificate; the CA signing key stays outside the pod and image. Only the Forwarder mounts the server private key. Runs receive public CA trust alongside required public roots, with normal hostname/IP and expiry verification. Rotate through a controlled deployment restart, never silently disable verification. Certificate lifetime, renewal preflight and each client's trust wiring are specification/acceptance details; TLS support in every selected client is not yet proven.
3. Admission and revocation. Receiver uses an authenticated control channel that Runs cannot access, backed by an enforced OS/credential boundary rather than merely an omitted environment variable. Register only declared service scopes before Run launch. Revoke on every exit/timeout and invalidate old admissions after Receiver/Forwarder restart; bound any orphaned sentinel with a lease tied to the ticket-21 Run budget. Control-channel loss stops new Run admission. Forwarder restart starts with no valid sentinels; do not automatically restore authority from a persisted token list. Already-dispatched upstream requests may have unknown outcomes; revocation is not rollback.
4. Redirects and uncertain writes. Reject upstream redirects on Run-facing endpoints rather than relay Location to clients; configuration must name the canonical endpoint. Strip caller Authorization, Host and proxy/hop credentials, then attach only the configured service credential. Do not transparently retry mutations after timeout, disconnect or uncertain delivery. Report the uncertain operation for reconciliation under ticket 21 and the relevant Jira/Confluence contract. Define bounded request/body/response sizes and timeouts in the specification without inventing success after truncation or timeout.
5. Preventing bypass. Disable anonymous Grafana access, block direct Run access to unauthenticated telemetry backends, mount service credentials only in the Forwarder, and scope upstream roles/RBAC to approved operations. Do not claim ordinary pod-level network policy separates sibling containers: prove the actual routing/auth/OS boundaries and allowed Anthropic/telemetry-export exceptions. Any route lacking enforceable operation/rehearsal scope stays unavailable. Exact grants come from Eyes/ticket 33 and the integration specification; no live permissions are asserted.
6. Service readiness. Require the Forwarder/control/TLS boundary and mandatory Jira, Grafana and Kubernetes read routes to be ready before starting new Runs; receipt/pending-Notification behavior remains a separate Receiver contract, not automatic disposal. Confluence unavailability permits degraded operation with visible missing Memory per ADR 0009. Mid-Run failures are explicit tool/transport errors, with ticket 21 deciding overall outcome/recovery. No direct-upstream or real-token fallback, silent broadening of access, or automatic mutation replay. Telemetry export remains best effort per ADR 0010 and cannot become a mandatory Run gate.

After acceptance: consolidate in an ADR extending 0002 and clarifying 0007, update the Forwarder glossary, and graduate an integration/acceptance specification. That specification chooses concrete endpoints, trust/lease/time/size bounds, process identities/control transport, secret mounts, request policies, query-scope enforcement, and offline rejection/read-back tests. Ticket 12 owns exact tools/operations; ticket 19's prototype must follow the accepted transport/credential boundaries; ticket 21 owns Run refusal/retry/outcome behavior. No cluster, demo or live client invocation is authorized by these planning decisions.
