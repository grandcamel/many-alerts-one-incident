# Ticket 25 — first decision round accepted

The human accepted all four recommendations with “Agree.”

Standing decisions: one in-cluster venue (ADR 0007); a Change records an action rather than an Alert (CONTEXT.md:22-31); only the Mechanism is scored and repository adjudication Ground truth never enters Runs (ADR 0008:5,16-18); clearly labelled supported causal inference may pass without a directly observed Trigger (ADR 0014). Ticket 10's presenter path is ConfigMap edit plus flagd rollout, with symptom confirmation separate. This round does not reopen these choices or authorize execution.

1. Producer and coverage. Recommend one operator-controlled in-cluster action coordinator that performs the accepted presenter action and records its progress for every injection and undo, across primary and fallback Faults. It is separate from Runs and the Forwarder's read-only Kubernetes path; its mutation authority is operator-only and narrowly scoped. Record actions directly where they are requested/performed instead of relying on a passive watcher to infer actor, intent or success from rollout Events. Existing evaluations and Kubernetes Events remain independent supporting observations. No promise of complete audit coverage for arbitrary out-of-band edits: expose those as untracked/unknown when detected. This replaces the old unverified assumption that a small flagd watcher alone supplies a complete Change.
2. Record truth. Recommend a stable Change ID with linked append-only stages for request, accepted config write, rollout observation and served-value/evaluation verification, each with its own event/observation time and outcome. Include target environment/resource identity, intended flag/variant, observed old/new values where actually read, available resource versions, operator alias and explicit injection/undo intent. An accepted write, a healthy rollout, a served value and an application evaluation are different claims. Link actual evidence; unknown stays unknown. Never label provider read-back as proof every application evaluated the value, or rollout completion as proof of recovery. Symptom/recovery confirmation remains separate system evidence. Do not emit expected Mechanism, Ground truth prose, scoring hints or personal account identity.
3. Retrieval and presentation. Recommend a dedicated structured Change stream through the collector to Loki as the required Run-readable surface, queried through the approved Eyes/Forwarder path. Keep producer/source identity distinguishable from application logs and Run telemetry. Use the same Change ID for an optional derived Grafana annotation for the audience; annotation failure must not create a second authoritative Change or require a new annotation API for Runs. A Change is evidence of the action/stage it records, not proof that it caused an Incident. Queryability and provenance need acceptance proof, not just a successful export call.
4. Failure policy. Recommend recording intent durably and proving the Change retrieval path ready before a new injection. On partial actuation, uncertain dispatch or missing delivery, stop additional injections and expose the unresolved stage; reconcile actual config/rollout state rather than repeating the action blindly. Always preserve an operator recovery/undo path even when telemetry is down, recording recovery locally for later delivery and marking gaps. A loss of Change telemetry must not block safety recovery or make an existing Incident look complete. Do not automatically rerun models, create Incidents or prescribe diagnosis in response to a Change delivery failure.

Dependent next round: exact durability/capacity/retention and delivery bounds; per-target serialization/idempotency/restart recovery; clock/order and read-back semantics; actor identity and restricted grants; permitted out-of-band intervention, cleanup and offline/live acceptance cases. All four recommendations are accepted. Planning only; no scripts, Skill, collector or cluster changes.
