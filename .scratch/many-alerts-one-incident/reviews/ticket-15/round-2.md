# Ticket 15 — second decision round accepted

The human answered “agree” to all five second-round recommendations after accepting all six first-round recommendations. Current code and historical exporter capabilities remain as bounded in facts.md; the following are design choices, not existing behavior.

1. Correlation authority. Make the Receiver's Run ID the canonical identity. Explicitly map the native session identity to it when observed; do not assume they are equal or rely on an unverified flag. Associate a Run with every admitted Notification and every touched Incident, retaining zero/one/many relationships. An absent native session identity is visibly unknown, not a reason to invent a join. Incident associations describe observed outcomes rather than candidate reads presented as accepted Matches.
2. Separation and access. Mark Run telemetry with a dedicated service namespace and feed origin, separate from application telemetry. Keep Run/session/rehearsal IDs, Notification IDs and Incident keys as log fields/structured metadata rather than per-Run metric dimensions or Loki index labels. Derive per-Run dashboard usage from correlated event records; aggregate metrics remain bounded. Queries default to the current rehearsal; enforce the accepted read scope at the Eyes/Forwarder boundary, not merely through dashboard filters. Exact resource-to-label mapping and permission implementation are follow-on specifications for tickets 12/17.
3. Sanitized event contents. Retain lifecycle, operation/tool name, timing, success/error/denial category, safe diagnostic summary, usage when available, and verified source/query references. Do not forward complete assistant text, commands, arguments or tool output by default. Unknown event shapes produce an omission marker. Preserve provenance to distinguish recorded tool execution from a Run's own assertions. Sanitized telemetry is not a complete Transcript for citation auditing; ticket 24 must specify its separate evidence requirements without putting raw content or Ground truth into shared telemetry.
4. Storage and overload. Use a bounded in-memory export queue with no new persistent spool. On overload, discard oldest queued records, count the loss and expose gaps; on restart, treat unconfirmed delivery as unknown. Keep shared Run telemetry for 24 hours as the accepted demo retention default, with read access still limited to the current rehearsal. Do not automatically purge the system's telemetry or OPS/Confluence history. Exact queue byte/event limits, attempt budget and backend retention feasibility require a bounded implementation specification and offline tests; the queue must never block Incident work.
5. Delivery identity and audience truth. Give each Receiver-projected event a stable Run ID plus sequence identity before enqueueing, so retried sends do not become duplicate actions in the timeline. Retain event time and observation/ingestion time where available; show gaps and late arrival without fabricating missing events. Keep native export and Transcript-derived values visibly attributed and choose one source per displayed measure, never sum overlapping cost/token counters. Show missing final usage/outcome as unknown or incomplete; an exit code, quiet stream or delivery success alone does not establish Run success. Ticket 21 owns terminal success/failure classification.

After acceptance: consolidate policy into an ADR; graduate the telemetry integration/acceptance specification (field schema, queue bounds, actual native inventory, collector transforms, cumulative temporality on the intended venue, sanitization tests, delivery/restart failure tests, and dashboard queries). Runtime implementation, fresh Claude flag/model claims, cluster and live export acceptance remain outside this ticket.
