# Refusal and recovery contract for future Skill implementation

Planning artifact accepted through ticket 21; this is not installed Skill code or a claim of runtime enforcement.

1. Use only approved tools and operations. Never create junk/probe Incidents, switch permission mode, expose credentials or bypass the Forwarder.
2. If an intended mutation is explicitly denied before dispatch, one shorter evidence-backed Report attempt is allowed within the current work budget. Preserve citations and mark omissions; ticket 16 supplies its shape. Do not infer that every denial is caused by command length or repeatedly test the limit.
3. If dispatch may have occurred, stop mutation retry. Record the operation/reference for reconciliation through trusted responses and read-back. Do not treat a timeout as proof that nothing changed.
4. Preserve confirmed effects. A failure to write Memory, create a draft or export telemetry is not permission to repeat confirmed OPS work. Repair only the missing step under the relevant contract.
5. At cancellation/deadline, service authority is revoked. Do not attempt further external writes or recover by another tool; local result/usage flush is best effort and does not extend the deadline.
6. A later authorized retry is a fresh Run over reconciled outstanding work and newest admitted Alert states. Apply current Match rules, retain provenance and do not replay old commands. Human-owned correction and forced-completion rules remain ticket 14's.
7. State observed failures, partial results and uncertainty plainly. Distinguish a model/tool/transport refusal from a system Fault; do not fabricate usage, successful filing or a verified diagnosis.

Receiver classification, durable admission/journaling, retry gating and process containment are Receiver/Forwarder responsibilities, not promises a prompt alone can enforce. Implementation acceptance must exercise real caller boundaries.
