# Ticket 33 — second decision round accepted

The human accepted all five recommendations with “Agree.” Round 1 is also accepted. Installed confluence-as 1.1.1 exposes native draft create/update status, but its update fetches the current page then increments that version; no caller-supplied expected-version option or exact-version read option was found in the inspected page help. These are capability gaps to address in the specification, not permission to weaken accepted version or approval rules. Tenant behavior remains unverified.

1. Draft identity and conflicts. Keep an operator/Receiver-owned durable mapping from tenant plus OPS Incident ID to Confluence draft page ID, origin rehearsal, last confirmed page version and mutation receipt. Retain the OPS link as required by ADR 0009; titles and labels never authorize adoption. Record create intent before dispatch and reconcile an uncertain create through trusted receipts/read-back; if its identity cannot be established, hold that Memory step for human resolution instead of creating another draft. Updates require the exact previously reviewed/fetched draft version; a conflict holds the update for reread/review, not an automatic overwrite. The current CLI's read-then-increment is insufficient to bind a stale composed body to its source version; specify a narrow adapter or Forwarder-enforced expected-version contract and verify it before allowing updates. Reopening/corrections stay reviewable; Run publication remains forbidden.
2. Reference reads and minimum operations. Serve only manifest-listed reference page IDs whose current returned version and body digest match the approved snapshot; if the page changes, withhold it until fresh review rather than silently serving an unapproved latest version or assuming historical-version retrieval works. Permit draft create, read and expected-version update only for the registered current-rehearsal Incident scope, with native draft status explicit and verified. Restrict supporting metadata/space resolution to the IDs needed for these operations. No Run-wide CQL search, unrestricted space enumeration, attachments, comments, labels, moves, deletions, restrictions or publication. Query results and metadata must not leak other spaces/rehearsals. Exact transport operations, payload/body bounds and pagination belong in the specification; inability to enforce scope disables the affected route with disclosed degraded Memory.
3. Revocation during a Run. Apply manifest revocation immediately to new reads and reference admission; a rehearsal snapshot cannot override it. Track which reference versions each active Run received. If an active Run received a now-revoked reference, cancel it through ADR 0012's bounded cancellation/recovery path, hold subsequent model dispatch for operator review and reconcile already-confirmed/uncertain external effects. Do not imply cancellation erases context or rolls back OPS writes. Mark affected prior outputs for review and suspend related guidance promotion. Retry only through existing explicit operator recovery and spend rules, with a new admitted context; no automatic model retry. If exposure cannot be determined, conservatively treat active Runs admitted to that manifest as affected. A reference edit/version mismatch is unavailable context until reviewed, not silent approval of the new body.
4. Curator workflow and retention. Keep original drafts, source revisions, approval/revocation history and links available to humans across rehearsals, with no automatic deletion or re-exposure to new Runs. The curator owns publication, amendments and explicit archive/delete decisions; an archived/deleted approved page is withdrawn from the manifest. Unresolved duplicate/create/version conflicts remain visible as incomplete Memory work. Publication records reviewer, exact source draft/Incident revision, approved reference version/digest and source provenance. Retain separate draft and reference identities; human curation cannot retroactively make a draft approved evidence or erase earlier Report defects. Ticket 34 owns audience presentation of these states. This is a retention/workflow plan, not authorization to publish, archive or delete content now.
5. Acceptance and follow-up. Graduate a specification covering exact allowed native operations, manifests/mappings, body/version binding, current-rehearsal scope, non-admin grants and Forwarder/TLS enforcement. Offline tests exercise real client requests and policy boundaries, including absent/forged IDs, cross-space/rehearsal reads, publication-status bypass, changed versions/digests, stale update bodies, duplicate/uncertain creates, revoked references already delivered, pagination/metadata leaks and native draft read-back. Separate future tenant acceptance must verify native draft create/read/versioned update, human publication/read-only references, effective principal restrictions and lack of direct-route bypass using explicitly authorized disposable artifacts. No tenant state is inferred from CLI help or role names. Do not enable the affected Confluence capability until its acceptance passes; optional Memory degradation remains available and confirmed OPS work is preserved. No tenant calls, grants, spaces, credentials or model Runs are changed by this planning decision.

After acceptance: write an ADR and bounded integration specification; align tickets 32/34/36/37 and manifest/version/revocation audit inputs in ticket 39. Preserve prior accepted Memory/OPS authority and budget/recovery constraints. The two proposed space keys still require availability checks before provisioning.
