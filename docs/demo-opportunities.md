# What changed since the original onboarding branch

Review fixed points: common commit `6a3ecc2` (scope manifest closeout), original `demo-onboarding` tip `ca022cf` (16 later commits), and local `main` tip `796455a` (67 later commits), inspected on 2026-09-25. The original branch taught a second engineer to run the one Alert Compose demo against a dedicated JSM site. That is useful historical onboarding evidence, but its direct-token executable path was retired on `main` in `fdd0f95` under ADRs 0011–0013. The rebased branch now proposes a **future live design**, with the old source implementation returned to `main`'s guarded state.

| Original demo | Opportunity opened by later work | What can be shown now | Live acceptance still needed |
| --- | --- | --- | --- |
| One Alert Fingerprint keyed one Incident. | ADR 0006 makes the Incident span a Fault's Cascade and treats Match as an evidence-based Run judgment. | Storyboard the candidate decision, several accepted Fingerprint members, an ambiguous separate Incident, and human correction. | Qualified Fault/Alert menu, actual OPS candidate reads and mutation read-back. |
| Three one-off Runs were inferred from a container log. | ADR 0012 and the journaled Receiver separate durable admission, execution, effect and recovery. | Local admission-only replay and inspected held records; a future operator scene for failed/uncertain effects. | Guarded writer, containment, reconciliation and one-use dispatch permit at the real exchange. |
| One Jira-only Forwarder and a Run-held OAuth token. | ADRs 0011 and 0013 require mediated scoped TLS endpoints, including model auth behind the Forwarder. | Explain the service boundaries and refusal states. | Native client path, authentic grants, credential custody and per-effect receipts. |
| A model alias and Transcript estimate suggested readiness/cost. | Durable accounting starts from unknown population and must reserve before each attempt; qualification uses representative complete Fault lifecycles. | Show the hold policy and distinct estimate, provider actual and cloud-cost categories. | Authoritative opening/billing continuity, defensible exposure, current rates/limits and paid qualification. |
| The audience watched an unstructured log and a single Incident. | ADRs 0010, 0014 and 0018 define a sanitized correlated timeline, private citation audit, seven-section Report and reviewed audience Memory card. | Review local layouts, claim-link prechecks and status candidates with clear local-only labels. | Trusted capture/export, Eyes provenance, tenant source joins and human causal review. |
| Traffic stop/start was the presenter's action on a laptop. | ADRs 0007, 0008, 0015 and 0016 specify an intended DOKS venue, protected Fault/Change provenance and bounded teardown. | Present the intended scene and its preparation checklist. | Venue allocation, actual Fault behavior, stage observations and protected teardown handoff. |

The first proposed milestone is **one Fault → many Alerts → one Incident → supported Report**. It is the clearest expansion of the project's central claim. Recovery/budget visibility and reviewed Memory/Change are separate scenes so that a missing gate does not turn a source-only candidate into a live capability.

The [future storyboard](demo-runbook.md) gives the scene order and evidence gates. The [local closeout](../.scratch/many-alerts-one-incident/reviews/local-goal-closeout-2026-09-25.md) records which tickets remain externally gated. Dated single-alert measurements remain in `.scratch/demo-onboarding/live-check-2026-09-24.md` as historical evidence only; they do not qualify a future model.
